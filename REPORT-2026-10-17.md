# ADC fault investigation — 2026-10-17

## Bottom line

**The config is not the cause, and the ADC is almost certainly not fried.** Two
independent firmware subsystems are dead while core packet handling works. The
remaining suspect is firmware state in flash, and the fix is a re-flash.

**Current state: the ESC is hung and needs a power cycle.** It stopped answering
packets during my config restore (see "What I broke"). USB still enumerates; no
packet gets a reply on either node.

## What was ruled out (each tested, not assumed)

| Hypothesis | Test | Result |
|---|---|---|
| Config drifted over the week | read both blobs | **intact**, every value as left |
| Something in our app config | wrote firmware's own **default appconf** + ADC enabled, rebooted | still dead |
| UART app conflicting | `app_to_use = 2` (ADC only), rebooted | still dead |
| Something in motor config | wrote firmware's own **default mcconf**, rebooted | still dead |
| My write path corrupts the blob | wrote blob back unchanged, re-read | **byte-identical** |
| My float32_auto encoder is wrong | decode→re-encode 42 firmware-written fields | **42/42 byte-exact** |
| My terminal parser is broken | dumped *all* raw packets after `help`/`ping`/`faults` | **zero packets** |

## The actual signature

- `COMM_GET_VALUES`, `COMM_GET/SET_APPCONF`, `COMM_GET/SET_MCCONF` — all work
- **ADC input app** — dead (both channels report a hard `0.000 V`)
- **Terminal / COMM_PRINT path** — dead (no output from any command)

Two worker threads down, main packet handler up. That is a firmware-state
failure, not silicon.

## Why "the ADCs blew" doesn't fit

1. **Both channels died at the same instant**, on a config write — and ADC2 had
   nothing connected to it at the time.
2. **It recovered once**, via a soft reboot (ADC1 0.843 V, ADC2 0.520 V), then died
   again on the next config write. Dead silicon does not recover.
3. **The terminal subsystem died simultaneously.** That shares no hardware with the
   ADC pins. One fault explaining both has to be software.
4. A hard `0.000` is *not* what a disconnected ADC pin reads — floating measured
   0.345–0.520 V all session. Zero means nothing is sampling, not that the pin is open.

## Timeline of the original break

| Event | ADC |
|---|---|
| set `ctrl_type 8` + `voltage2_start 1.0` | **working** — 0.846 V / 3.299 V |
| set `voltage_min 0.5` + `hyst 0.10` | **dead** |
| soft reboot | **recovered** — 0.843 V / 0.520 V |
| set `ramp_time_pos 0.5` (+ motor `time_ramp 0.4`) | **dead** |
| power cycle, soft reboots, one week off | still dead |

Both breaks immediately follow an appconf write. The one recovery was a soft reboot.
No config value explains it — firmware defaults fail identically.

## What I broke

Restoring config after the default-config tests, I sent three large flash writes
back to back (~1.2 s apart): default mcconf, then backup mcconf, then backup appconf.
The readback mismatched and the ESC stopped responding. VESC commits config to flash
with interrupts disabled; stacking writes that fast is likely what hung it.

**Both configs are backed up** in `backups/` (`app-*.bin`, `motor-*.bin`, plus the
firmware defaults). Nothing is lost. Use `restore_config.py`.

## Next steps, in order

1. **Power cycle.** Should restore comms.
2. **`python3 restore_config.py`** — rewrites both configs from backup, one at a time
   with proper settling.
3. **Test PPM** — `python3 vesc_conf.py app set app_to_use 1`, reboot, then
   `python3 vesc_read.py` and watch the PPM section with the signal applied.
4. **Re-flash firmware 6.06** from VESC Tool's firmware page. This is the fix the
   evidence points to. Config is backed up and restorable in one command.
